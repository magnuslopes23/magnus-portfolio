# Magnus Lopes — Portfolio

A conversion-focused personal portfolio for a freelance software engineer. The site is intentionally designed like a premium SaaS product rather than a conventional CV page.

## Architecture

- Next.js App Router for server-rendered/static-first pages, metadata, sitemap and route handlers.
- React for the few interactive elements that need client state: mobile navigation and contact form.
- Native CSS design system to minimise dependencies, keep bundle size low and preserve full visual control.
- Centralised content in `data/site.ts` so copy, projects, social links, services and skills can be changed without touching layout code.
- `/api/contact` route validates submissions and sends mail using Resend's HTTP API. A honeypot field blocks basic form bots.
- Structured data (`Person` schema), canonical metadata, Open Graph metadata, `robots.txt` and `sitemap.xml` are generated by Next.js.

## Why this stack

Next.js is a strong fit because the portfolio needs excellent SEO, static-first performance, maintainability, route-level metadata and straightforward deployment. Vercel provides zero-config Next.js deployment and preview deployments from Git. Netlify also supports Next.js, but Vercel is the default recommendation for this implementation. GitHub Pages is suitable only if the contact API is removed or replaced with an external form provider because Pages is static hosting.

## Local development

```bash
npm install
cp .env.example .env.local
npm run dev
```

Open `http://localhost:3000`.

## Personalisation checklist

Edit `data/site.ts` first:

1. Replace `hello@your-domain.com`.
2. Replace the Cal.com URL.
3. Replace GitHub and LinkedIn URLs.
4. Review project wording and remove anything that cannot be made public.
5. Replace testimonial placeholders only with quotations you have permission to publish.
6. Add actual client/company logos only where branding permission exists.
7. Add measurable case-study results when you can substantiate them.

Then set `NEXT_PUBLIC_SITE_URL` to the production domain.

## Contact form setup

The included endpoint uses Resend via HTTP, so no email SDK dependency is required.

Set:

```bash
RESEND_API_KEY=...
CONTACT_TO_EMAIL=...
CONTACT_FROM_EMAIL="Portfolio <portfolio@your-domain.com>"
```

The sending domain/address must be valid with the email provider. For higher-volume public forms, add Cloudflare Turnstile or another privacy-conscious anti-abuse layer plus persistent rate limiting.

## Deployment — Vercel

### Git workflow

1. Create a GitHub repository and push this folder.
2. Import the repository into Vercel.
3. Add the environment variables from `.env.example` in Project Settings → Environment Variables.
4. Set your custom domain.
5. Deploy. Each subsequent push creates a deployment; pull requests can receive preview deployments.

### CLI workflow

```bash
npm i -g vercel
vercel
vercel --prod
```

## Deployment — Netlify

1. Push to GitHub.
2. Create a new site from the repository in Netlify.
3. Use the detected Next.js build settings.
4. Add the same environment variables.
5. Attach your custom domain.

## GitHub Pages option

GitHub Pages does not provide a Node/serverless runtime for `/api/contact`. To use Pages:

- convert the site to a static export, and
- replace `/api/contact` with an external form endpoint such as Formspree or Basin.

For the current implementation, Vercel is the cleaner deployment target.

## SEO strategy

### Technical

- One clear H1 aligned with the commercial positioning.
- Semantic landmarks and heading hierarchy.
- Server-rendered indexable content.
- Canonical URL, sitemap and robots configuration.
- Person structured data.
- Open Graph and Twitter metadata.
- No critical text rendered only after client-side JavaScript.
- Responsive layout and reduced-motion support.

### Content

Create dedicated pages over time for high-intent topics rather than stuffing the home page with keywords:

- `/services/software-development`
- `/services/automation`
- `/services/api-integration`
- `/services/cloud-solutions`
- `/work/<case-study>`
- `/insights/<article>`

Target problem-specific search intent: “workflow automation developer Ireland”, “Python automation consultant”, “API integration developer”, “internal tools developer”, and adjacent terms only when they accurately describe the service.

Each case study should contain: business context, constraint, architecture/decision, implementation, measurable outcome, and lessons/trade-offs.

## Personal branding strategy

Positioning hierarchy:

1. Business outcome: reliable digital products and operational systems.
2. Engineering identity: software engineer with automation, data and cloud depth.
3. Differentiator: ability to convert ambiguous operational workflows into maintainable systems.
4. Proof: case studies and specific outcomes.
5. Technology: supporting evidence, not the headline.

Avoid broad claims such as “10x engineer”, generic percentage improvements, fabricated client logos, or long technology walls without context.

## Conversion strategy

The page supports three visitor intents:

- Commercial buyer → “Book a discovery call” and project brief form.
- Technical evaluator → case studies, skills and engineering process.
- Recruiter/hiring manager → positioning, projects, social profiles and contact.

Recommended production improvements:

- Add a short pre-qualification field for expected project size or engagement type.
- Track CTA clicks, form starts and successful submissions using privacy-conscious analytics.
- Add a dedicated `/work` case-study page for each strong project.
- Add real testimonials with role/company attribution and permission.
- Add a downloadable résumé for hiring traffic while keeping the homepage commercially focused.
- Test hero CTA wording and case-study order based on actual conversion data.

## Performance and accessibility

- No third-party UI framework or animation library.
- No external font request by default.
- Minimal client JavaScript.
- Native semantic elements and labelled inputs.
- Keyboard-visible focus states.
- High contrast dark palette.
- `prefers-reduced-motion` support.
- Mobile navigation exposes `aria-expanded` and a controlled region.

Before launch, run Lighthouse and test with keyboard-only navigation, VoiceOver/NVDA, 320px mobile width, slow 4G, and no-JavaScript rendering of critical content.

## Implementation plan

- Replace all placeholders and confirm public-safe case-study copy.
- Connect real domain, booking link and email delivery.
- Add favicon/brand mark variants and a professional portrait if desired.

### Phase 2 — Proof
- Publish 2–4 detailed case-study pages.
- Collect verifiable testimonials.
- Add real screenshots/architecture diagrams with confidential data removed.

### Phase 3 — Authority
- Publish technically substantive articles tied to buyer problems.
- Add project-specific structured data and internal linking.
- Create an `/about` page for deeper career context without crowding the homepage.

### Phase 4 — Optimisation
- Add analytics and conversion events.
- Measure booking CTA clicks, contact form completion and traffic by landing page.
- Refine headline, CTA wording and service pages based on observed behaviour.
